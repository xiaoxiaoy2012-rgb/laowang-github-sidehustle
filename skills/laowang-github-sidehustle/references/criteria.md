# 判断标准

不默认给所有人同一张“赚钱分数榜”。优先选择用户接得住、需求可验证、交付可控的项目。

| 维度 | 要找的证据 | 常见误判 |
|---|---|---|
| 买家与痛点 | 用户描述具体任务、现有付费替代、重复需求 | Issue 多等于需求大；下载多等于愿付费 |
| 改造价值 | 缺失的业务流程、行业输入输出、交付包装 | 翻译几个按钮就有竞争力 |
| 上手成本 | 安装步骤、运行依赖、外部服务、硬件 | Python 一定容易；仓库小一定轻 |
| 交付成本 | 推理/API支出、维护、售后、数据迁移 | 免费源码等于零成本 |
| 授权条件 | LICENSE 原文、模型与素材授权、依赖条款 | 有许可证等于可无条件闭源转售 |
| 可重复销售 | 同一能力覆盖多人、交付能标准化 | 每单重新开发也称睡后收入 |

默认结论使用：值得小试 / 需要补证据 / 当前不适合，并说明决定性理由。比较时保持同一用户假设。

没有明确许可证、条款含糊或商业授权不清时，标为待核查，不宣称可以直接售卖。GPL/AGPL 不等于禁止收费；具体义务取决于版本、修改、分发、网络服务等实际使用方式，应读取原文，不作一刀切判断。MIT/Apache 也有声明保留等条件。

只读 README 可支持“项目宣称能做什么”，不能支持“已部署成功”“有客户愿付费”。提供部署/性能/效果结论时，应给相应实测证据。

需求实验示例：为某类用户做一段输入输出演示，询问其现有做法和付费意愿；只有明确提出试用或采购需求，再投入完整开发。实验时长与访问人数由用户条件决定，不凭空规定收入目标。
